- **Refonte — « Reprendre » devient local et restaure la file d'attente** (2026-08-13) : demande utilisateur (« le multi-appareil, on oublie ; par contre Reprendre doit aussi reprendre la liste de lecture »). **Nouveau `player/resumeState.ts`** : un point de reprise `{ trackIds[], index, positionMs, updatedAt }` miroité dans `app_settings` (`playback.session`) — la file ne vivait que dans le lecteur natif Media3, qui meurt avec le process, donc tuer l'app perdait tout sauf la piste. Écriture depuis `dispatchPlayerEvent` (donc premier plan **et** headless) : **sans attendre** aux moments décisifs (changement de piste, pause/reprise, fin de file) et **throttlée à 5 s** sur les ticks de progression, la position étant seule à bouger entre deux ticks ; la position exacte vient de `getPlaybackSnapshot()`, seule source à la seconde. Une file contenant un `mediaId` vide fait abandonner la photo plutôt qu'enregistrer une file trouée qui décalerait l'index. **`ResumeCard` réécrite** : résolution des ids contre `tracksById`, les fichiers disparus sont **omis avec recalage de l'index** (piste active si encore là, sinon la première suivante disponible ; position remise à 0 si ce n'est plus la piste interrompue), puis `playQueue(tracks, index, 'resume')` + `seekTo` ; sous-titre « à 2:41 · 7 titres à suivre », pochette au lieu de l'icône `cast`. `computeResume` est exporté pour la tuile d'accueil du lot suivant. **Purge du handoff** : `REMOTE_STATE_KEY`, `buildPlaybackPush`, `deviceName`, les types `PlaybackStatePush/Pull` et les réglages `playback.lastLocalAt` / `handoff.dismissedAt` disparaissent ; nouveau `db.deleteSetting` (le stockage n'avait qu'un `setSetting(key, string)`). `clearResumePoint()` est appelé à la déconnexion (base partagée entre comptes). **Côté backend** (commit séparé, **à déployer**) : entité `PlaybackState` + repository supprimés, `PlaySyncService` allégé de `upsertPlaybackState`/`serializePlaybackState`, test correspondant retiré, migration `Version20260813090000` (DROP TABLE, réversible). - **Correctif — le tri « Ajouts récents » affichait l'ordre alphabétique** (2026-08-13) : bug utilisateur. **Cause** : `LocalTrack.creationTime` vient de `AssetMetadata.creationTime` d'expo-media-library, qui mappe `MediaStore…DATE_TAKEN` (colonne EXIF **jamais renseignée pour l'audio**, vérifié dans `AssetMapper.kt:110` / `AssetField.kt:17`) — elle est nulle partout, donc `sortTracks('recent')` retombait intégralement sur son départage `compare(a.title, b.title)`, soit exactement le tri Titre ; la rangée « Récemment ajoutés » du Dashboard souffrait du même mal. **Correctif** : nouvelle colonne `tracks.first_seen_at` (migration **v16 additive**, pas de `DELETE FROM tracks` — les lignes existantes sont rétro-remplies avec `COALESCE(creation_time, modification_time)`, + index), posée à l'insertion par `upsertTracks` et **préservée aux ré-écritures** via `COALESCE((SELECT first_seen_at FROM tracks WHERE id = $id), $now)` dans le `VALUES` (l'`INSERT OR REPLACE` l'effacerait sinon, et un simple renommage/ré-tag ferait remonter un vieux morceau en tête — comportement vérifié en sqlite3). `LocalTrack.creationTime` → **`addedAt`** (le champ mort est remplacé, pas doublé) ; `TrackRow` garde `creationTime` en écriture (coût nul, utile si expo corrige un jour le mapping). **Bonus ergonomie** : `SortBar` n'est plus un bouton qui cycle titre → artiste → récent (jusqu'à 3 taps pour atteindre le dernier) mais ouvre un `SortSheet` (BottomSheet, gabarit `QuickActionsSheet`, critère courant coché) → 1 tap pour n'importe quel tri. ⚠️ **Non testé sur appareil** (la migration v16 et le premier scan après migration) ; tsc + lint + prettier verts.

- **Correctif — session résiliente : plus de déconnexion sur panne réseau, app utilisable hors-ligne** (2026-08-13) : bug utilisateur (« je suis régulièrement déconnecté », « l'app devrait marcher sans connexion »). **Cause racine dans `AuthProvider.doRefresh`** : le `catch` appelait `clear()` sur *n'importe quelle* erreur, or `authApi.refresh` lève aussi sur panne réseau (`ApiError(0)`) — avec un access token d'1 h et un refresh tenté à chaque retour au premier plan (`SyncProvider`), un Wi-Fi capricieux au mauvais moment effaçait de SecureStore un refresh token pourtant valide 90 jours. Désormais un helper `isSessionRejected(error)` ne déconnecte que sur un **4xx explicite** (hors 429) ; réseau (status 0) et 5xx laissent la session intacte et basculent un nouveau champ `sessionOnline` à faux. **Le gate d'auth ne dépend plus du réseau** : au démarrage, la seule présence d'une session en SecureStore fait passer `status` à `'authenticated'` (le renouvellement d'un token périmé part en fond sans pouvoir rétrograder le statut) — l'app s'ouvre donc sur la bibliothèque locale en mode avion au lieu de l'écran de connexion. Nouveau `OfflineBanner.tsx` (icône `cloud_off`, informatif, aucun blocage) en tête du Dashboard, affiché si `sessionOnline === false` **ou** si la dernière synchro a rendu `'offline'`. **Côté backend** : `JWT_TOKEN_TTL` 3600 → **86400** (moins de renouvellements = moins de dépendance réseau) et `gesdinet.single_use` **true → false** (la rotation à usage unique rendait la session irrécupérable si l'app était tuée entre la réponse HTTP et l'écriture du nouveau jeton) ; `ttl_update: true` conservé. **Bug de déploiement corrigé au passage** : le `rsync --delete` de `deploy.yml` n'excluait pas `config/jwt`, gitignoré donc absent du checkout → chaque déploiement supprimait la paire de clés JWT de production. ⚠️ **Non testé sur appareil** (mode avion + kill + relance, retour du réseau) ; ⚠️ **vérifier que le `.env.local` du VPS ne surcharge pas `JWT_TOKEN_TTL`**. tsc + lint + prettier verts.
